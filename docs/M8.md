# M8: Sunroom on This Computer

Sunroom 0.14.0 is out, and the installers were made one command each on 2026-10-22 (ADR 0037).
Trying them in virtual machines the same day, the owner asked for three things:

1. **No prompt on a Linux screen.** A Linux screen that finds its Sunroom by itself showed
   Chrome's one-time "allow local network access" prompt: the browser's policy was written only
   at install time, for the address given then. It should just work.
2. **Ubuntu's browser.** The Chromium snap would do, unless Google Chrome is better for a reason.
3. **Sunroom on any computer, chosen on the screen.** Not only a Pi: the person who pasted the
   command should, as the first thing the screen shows, choose between running Sunroom on this
   computer and using one that already runs elsewhere, each with words that explain it to
   someone who has never set up a server.

This file is the plan and the record (ADR 0038). Its tasks are ticked with their commits.

## What exists

- **The screen's first page** (`frontend/src/screen/pages/WelcomePage.tsx`) said "Let's get this
  screen set up." with **Start**, which led to **Where Is Your Sunroom?**: On Your Network, Run It
  on This Screen (Sunroom OS only) and Somewhere Else.
- **Run It on This Screen** (M7 T16) starts the Docker setup the Sunroom OS image carries, through
  the root helper's `run-sunroom`. No other screen can run Sunroom; a Pi can at install time
  (`install.sh --with-sunroom`, Docker).
- **The server** ships only as the Docker image. Its backend already runs as a plain program on
  macOS and Linux (`just dev`, the e2e server): what it lacks is a package with the built app and
  its version inside, and a few things Windows needs (the agents' map, 2026-10-22: `fcntl` for
  the instance lock, a directory fsync in restore, `os.execv` to restart after a restore, and
  `os.getuid` in one message).
- **The browser's policy on Linux** (Chrome's Local Network Access allowlist) is written by the
  installer, with sudo, for the address given with `--url`; only a Pi has the root helper that
  lets Sunroom Screen rewrite it when the address changes.

## Decisions

| Question | Decision |
|---|---|
| The Linux prompt | **The root helper on every Linux screen**: the installer puts `/usr/local/sbin/sunroom-kiosk-root` and its sudoers rule there with the policy (it asks for sudo for the policy already), and the Linux adapter writes the policy through it whenever the screen's address changes, as a Pi does. A screen set up before has no helper and still asks once. |
| Ubuntu's browser | **Google Chrome stays** (ADR 0037). Checked in an Ubuntu 24.04 machine: the Chromium snap reads its policy only from `/etc/chromium-browser/policies` (a blocklist policy there blocked a page; the same file in `/etc/chromium/policies` did nothing); its sandbox hides hidden folders in the home folder, where the screen's profile lives; and snapd holds a running snap's updates back with a notice for up to 14 days, then updates it anyway (snapcraft's refresh awareness): a wall's browser never closes, so the notice would keep coming on the screen. Each could be worked around; together they make a worse kiosk than Chrome's own package, which updates with the system and keeps running until the nightly restart. |
| The first page | **Two ways on, side by side** (one above the other in portrait): **On This Computer**, "Sunroom runs right here." with **Run Sunroom Here**, and **On Another Computer**, "Your family already has a Sunroom." with **Find Your Sunroom**. Each says what it is and when to choose it. Run Sunroom Here opens **Setting Up Sunroom** (the steps with a percent, why it stopped with **Try Again**, and **Back**); Find Your Sunroom opens Where Is Your Sunroom?, now On Your Network and Somewhere Else. A Sunroom OS screen with no network joins Wi-Fi first, then goes the chosen way. A computer that can't run Sunroom shows On Another Computer alone. |
| How Sunroom runs on a computer | **As a program for this user**, installed by Sunroom Screen with uv, as Sunroom Screen itself is: the release's server wheel (`sunroom-X.Y.Z-py3-none-any.whl`, the backend with the built app inside), checked against the release's `SHA256SUMS`, with the release's constraints file (`sunroom-X.Y.Z-constraints.txt`, from `backend/uv.lock`) so it runs the versions the image runs. Not Docker: on a Mac or Windows that means Docker Desktop (an administrator, a licence to accept, a virtual machine, on Windows a restart), and `get.docker.com` doesn't know common desktop Linuxes (Mint, Pop!_OS). The Docker ways stay: Sunroom OS's own setup, `install.sh --with-sunroom` on a Pi, and every server (DEPLOY.md). |
| Where it keeps the family's data | Linux `~/.local/share/sunroom`, macOS `~/Library/Application Support/Sunroom`, Windows `%LOCALAPPDATA%\Sunroom`, created for this user only. Backups go where they always do, into the data's `backups/`. |
| How it keeps running | Linux: a systemd user service, `sunroom.service`, restarted when it fails and kept running after sign-out (`loginctl enable-linger`, when allowed). macOS: a LaunchAgent, `app.sunroom.server`, under `caffeinate -i` so the Mac doesn't sleep while Sunroom runs. Windows: Sunroom Screen starts it, with no window, when it starts and whenever it stops answering, and keeps the computer from sleeping meanwhile. A Linux screen holds a sleep inhibitor while it has Sunroom. |
| Its address | Port 8080, or the next free one up to 8099. Phones open `http://<computer>.local:<port>` on a Mac and on Linux with avahi, else `http://<IP>:<port>` (Windows' own name lookup is unreliable). Sunroom Screen announces it on the network (`_sunroom._tcp`), so other screens find it on any port. |
| Which computers | Raspberry Pi OS and other 64-bit Linux, Macs with Apple silicon, and Windows (x64; on ARM through an x64 Python). **Not Intel Macs**: `cryptography` 49 and later ship no Intel Mac wheel (Sunroom needs 50), so there they show On Another Computer alone. |
| Updates | Sunroom Screen keeps the program at its own version: after it updates itself it installs the server wheel of that release; This Screen's **Update Sunroom Too** installs the newest. A new version that doesn't answer within five minutes is put back. The server says it's a `computer` install, and its About page says Sunroom Screen keeps it up to date. |
| Removing it | `sunroom-kiosk sunroom remove` stops it and removes the service and the program; the uninstallers run it and ask before deleting the family's data (kept unless they say so). |
| Releases | The release's files gain the server wheel and its constraints file (in `SHA256SUMS` like the rest). The repo's backend version stays 0.0.0; the release workflow stamps the version into the wheel when it builds it, and the server reads it from its package. |
| Trying a change | `just kiosk-serve` serves the server wheel too, and the installers take it (`--server-wheel`, `-ServerWheel`), as they take Sunroom Screen's (`--agent-wheel`). |

### T3 The server as a program

- [ ] Done
- The built app inside the backend's package (`sunroom/static`, hatch `artifacts`, gitignored),
  found when `SUNROOM_STATIC_DIR` isn't set; the version from the package's metadata when there's
  no build info; `SUNROOM_INSTALL_KIND=computer` and its update words; the data folder created
  for this user only. Windows: a portable instance lock, no directory fsync, a restart after a
  restore by exiting with 75 (Sunroom Screen starts it again; POSIX keeps `execv`), no
  `os.getuid`, UTF-8 for its text files.

  constraints file.
- **Tests:** the version and static fallbacks, the lock, the install kind's words.
