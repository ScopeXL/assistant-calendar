# ADR 0035: Sunroom Screen: the agent, This Screen, discovery, Releases, and the keyboard's number row

- **Status:** Accepted
- **Date:** 2026-10-20

## Context

- Sunroom 0.12.0 went on the owner's wall and phones. On 2026-10-20 the owner asked for two small
  wall fixes (the keyboard's number row, and the Hours view's now line drawn over the day heads)
  and for a plan: a flashable "Sunroom OS" for a Raspberry Pi, the device's own settings as an
  overlay on the wall, and one install command per OS that ends on a page which finds Sunrooms on
  the network. `docs/M7.md` is that plan, with the research, the design and every decision; this
  ADR keeps the ones that change an earlier decision or that a later session would otherwise have
  to rediscover (PLAN §15, M7). It is started with batch 0's first task and gains a row with each
  task after.

## Decision

| Question | Decision |
|---|---|
| The keyboard's number row | **Gone** (reverses that part of ADR 0032). The letters page (the `text` and `password` layouts) is the three rows of letters again; **123**, the bottom-left key, switches to the numbers and symbols, whose first row is `1234567890`; the number pad for times, PINs and codes is unchanged. The row cost a row of board on every field (64 px, 72 in portrait) and the family reached for 123 anyway |
| How a screen finds a Sunroom | **`GET /api/discover`**, public and `no-store`: `{sunroom: true, id, version, setup_complete, name, url}`. The **id** is `app_meta.instance_id`, a UUIDv7 made once (by the migration for an existing row, at boot for a row that lacks one) and carried by every backup and restore, so a screen whose Sunroom moved to a new address or a new card finds it again by id. **The household's name only to a local address**: the request's Host (after a home proxy's `X-Forwarded-Host`) is an IP literal, `localhost`, the container's own name, a single-label name or a LAN-suffix name, the Host rule's own list, lifted into `web/hosts.is_local_name`; a page rebound from the internet carries its public name and gets `null`. `url` is SUNROOM_ADVERTISED_URL or `null`. Not in "Recently reached at", like `/api/health`. The server doesn't announce itself over mDNS: a container on Docker's default network can't multicast to the LAN, so an all-in-one Pi's avahi file does it (T2) |
| The wall page and the agent | **The launcher names the agent on the address**: `/display?dimmer=…&screen=<port>`. **The server widens one document's CSP**: a `/display` request with exactly one `screen` from 1024 to 65535 gets `connect-src 'self' http://127.0.0.1:<port>`; every other page and port keeps `connect-src 'self'`. **The page reads the port once, at its start, and remembers it nowhere** (a page loaded without it has the plain policy, so a remembered port would only make blocked calls and CSP reports), and nothing calls the agent without it. Because the wall's rooms change the address and drop the parameter, **a fresh reload on such a wall goes to the launcher's address** instead of reloading the room's (the remembered room comes back by itself, ADR 0030). The agent's state is a query, polled every 30 s and kept current by its event stream; `null` when there's no agent or it doesn't answer |
| Settings → This Screen | **A Settings page, after Display**, so the PIN that guards Settings guards it too, and only on a wall whose agent answers (`usePages` drops it otherwise, so a phone never lists it). **The agent decides what it shows**: each row and button needs its capability, so a computer gets Quit and Open Network Settings and no Rotation or Wi-Fi. **What can't be undone asks first** (Shut Down: it stays off until it's unplugged; Change Address: it leaves this Sunroom), each with a button that says what it keeps; Restart doesn't ask (low harm, the screen is back in a minute). Its changes go to the agent only, never to the server, and a refusal shows the agent's own plain sentence |
| The screen's own pages | **A third shell from the same frontend** (`frontend/src/screen`, `screen.html`, `vite.screen.config.ts`), built by `pnpm build` into the agent's package (`static/`, gitignored, in the wheel as an artifact) and served by the agent with a fresh CSP nonce, as Sunroom serves its own: the wall's tokens, keyboard, toasts and parts, so the family never meets a second design. Its router is a store of six paths and the history API, not a library. It talks to its own agent on its own origin (`noteOwnScreenAgent`), with the wall's client and hooks. It decides little: the agent's state says where things stand, and each page follows it (a chosen Sunroom opens; Can't Reach and This Screen go back when it answers). Its theme is Auto by the time of day; no service worker |
| The Pi and Linux | **Linux** (`platform/linux.py`, any desktop and the Pi's base): power through logind (`systemctl reboot`, `poweroff`), Wi-Fi through NetworkManager's `nmcli`, and **a Wi-Fi password never on a command line** (any user can read those): the connection is added without it and brought up with `passwd-file /dev/stdin`. Before the browser's first start, the launcher's waits (the desktop, a minute for the clock) and X11's no-blanking. A desktop can Quit and doesn't turn its picture. **The Pi** (`platform/pi.py`, by `/proc/device-tree/model`) turns the picture (`wlr-randr`, or `xrandr` on X11) and **touch follows it through labwc**: `labwc-rule.py --rotate N --output NAME` maps Sunroom's touch entries to the output (wlroots then turns touch with it), and only without an output name writes a calibration matrix, so touch is never turned twice; labwc rereads rc.xml on SIGHUP. The saved rotation is applied each time the agent starts. **Root** only through `/usr/local/sbin/sunroom-kiosk-root` (`sudo -n`, the browser's policy, apt, `update.sh`); a Pi installed before 0.13.0 has none and nothing is tried. Sunroom OS is marked by `/etc/sunroom-os` |
| Sunroom Screen's updates | **The agent updates itself from GitHub Releases**: the newest tag (as Sunroom's own check), then that Release's `SHA256SUMS`; an update is "available" only once its wheel is listed there (a tag whose files aren't up yet isn't one). The wheel is downloaded, its sha256 checked (a mismatch stops it) and kept beside the running one. **A separate process applies it** (`sunroom-kiosk update --apply`, in its own `systemd-run --user` unit on Linux so restarting the agent's service doesn't take it down, standard library only once it starts, since the package is replaced under it): `uv tool install --reinstall`, restart the service, and wait 60 s for the new version to answer on 127.0.0.1; otherwise the previous wheel goes back, the service restarts again, and a note makes This Screen say "The update didn't start; the previous version is back." **Nightly** at the start of the sleep hours (from Sunroom's `/api/display/state`; 03:30 without them): the check, and with Install overnight the update; on Sunroom OS a restart when `/run/reboot-required` asks for one (unattended-upgrades installs the security updates). **Install overnight by default on Sunroom OS, Off for an install**, as Sunroom's own check is off until asked (GitHub sees the address). Run from a checkout, the agent has nothing to update from (`NoUpdates`). **An all-in-one Pi** can update its own Sunroom too (`update_sunroom`, through the root helper's `update-sunroom`, which runs `update.sh`), offered only while it shows that Sunroom and the Sunroom is behind |
| The installer | **One bootstrap for the Pi and Linux** (`kiosk/install.sh`, picked by `uname`, bash 3.2-safe; macOS joins in 0.14.0 and Windows gets `install.ps1`). It installs uv (pinned) when there's none, then **Sunroom Screen from its own version's GitHub Release**: the wheel's sha256 is checked against the Release's `SHA256SUMS` before `uv tool install --python 3.14` (`--agent-wheel FILE` tests a local build). **The rest of `kiosk/` comes from the same tag** (it was `main`, or `--version`'s tag), so the files and the program always match; `--version` now picks only Sunroom's image. **Every file it writes comes from `kiosk/files/`**, no heredocs, the same files Sunroom OS's image will copy. On a Pi it adds the root helper and its sudoers rule (`visudo -c` first) and retires the helper's and the timer's units; the unit's `ExecStart` stays `~/.local/bin/sunroom-kiosk`, now the agent's command, which runs the agent when given no command, so a Pi installed before is upgraded in place, pairing kept. **Another Linux computer** gets the screen alone, with no packages and no system settings: the agent, the user unit, an XDG autostart entry, and `sudo` once for the browser's policy (it has no root helper, so for an address found later the browser asks once). **`--url` is optional**: without it the screen's own pages find the Sunroom. **`--dry-run`** prints the plan for the computer it runs on and changes nothing; CI runs it on Ubuntu, macOS (`/bin/bash`, 3.2) and Windows (Git Bash) |
| Windows | **For the person signed in, with no administrator and no service** (`kiosk/install.ps1`, PowerShell 5.1-safe, `irm … \| iex`): uv and the checked wheel as on Linux, a shortcut in the Startup folder to **`sunroom-kioskw`** (the same command as a gui-script, so no console window; with no console it writes its log to `sunroom-kiosk.log` beside its settings), and it starts it. **The browser's policy goes under `HKEY_CURRENT_USER`**, which a user may write and Edge and Chrome both read, written by the agent itself at every start and rewritten when the address changes (`platform/windows.py`, `winreg`); `policy --remove` takes only Sunroom Screen's keys out again. Power is `shutdown /r` and `/s`; Wi-Fi, rotation and brightness are Windows' own (This Screen has Open Network Settings; the page dims itself). **Updates on Windows** can't replace a running program's files, so the apply step became its own standard-library file (`apply.py`): the agent copies it out and runs it with the Python its environment came from, and it asks the agent to quit (This Screen's own Quit) before uv replaces anything, then starts `sunroom-kioskw` again. `-Uninstall` is the installer's (a running tool can't uninstall itself on Windows), not a `sunroom-kiosk uninstall` command |
| GitHub Releases | **Each release is a GitHub Release too** (since 0.13.0): the deploy skill's `just github-release` makes it, with the CHANGELOG section as its notes, and `release-assets.yml` builds its files on GitHub when the tag is pushed (Sunroom Screen's wheel with its pages, the installers, and `SHA256SUMS`, uploaded last so it never names a missing file), waiting ten minutes for the Release and making a draft otherwise. **Nothing is uploaded from the Mac**, so the files come from the tag's own code on a clean runner. **Sunroom Screen carries VERSION** (its pyproject and its `uv.lock` entry, written by `just bump`, checked by `check_release_meta.py`), because its wheel is named for it and its updates compare it; the backend and frontend stay 0.0.0. Sunroom's own update check stays on tags (ADR 0032) |
| Sunroom Screen, the agent | **One process, `sunroom-kiosk run`** (`kiosk/agent/`, Python 3.14, FastAPI): the launcher and the screen helper rolled into one, plus an API on **127.0.0.1:7800** that the wall page and the screen's own pages call. **Who may call it:** a loopback Host only (`127.0.0.1`, `localhost`, `[::1]` with its port: a page rebound to 127.0.0.1 still sends its own name); CORS for exactly two origins, the Sunroom this screen shows (from its config, so it moves with the address) and the agent's own, never credentials, and `Access-Control-Allow-Private-Network` on a preflight that asks; every change needs `X-Sunroom-Screen: 1` and, from a page, one of those two origins. **Its settings** stay the bash-sourceable `~/.config/sunroom-kiosk/config`, rewritten in place (comments and keys it doesn't know kept). **What it can do** is the platform adapter's `capabilities`, which the pages show buttons for. **The screen helper** keeps its code and tests, on a daemon thread with a stop event, so it still never leaves a wall dark. **Shape names** all start with `Screen` (`ScreenStateOut`…), so the frontend's two generated schemas never share one. **The browser is watched through DevTools** on the port it picks (`--remote-debugging-port=0`, `DevToolsActivePort`): the page is Sunroom's when its title is Sunroom, it carries the nonce meta and its root has drawn something; nothing is injected. A pipe (`--remote-debugging-pipe`) would expose no port, but Python can't hand a child fds 3 and 4 without `preexec_fn` (unsafe with threads), and Windows can't at all |

## Consequences

- The keyboard: no schema or API change. `ui/Keyboard` lost its `DIGITS` row; `Keyboard.test.tsx` and the
  `shell.spec` dock case check that the first row is the letters' and that 123 reaches the digits.
- Noticed and left as it is: the symbols page's last row (ten symbols and a Delete one and a half
  keys wide) is about 1004 px against the 960 px box of keys in landscape, where it overhangs the
  box but stays in the dock, and 1096 px in portrait, where its first and last keys lose 8 px at
  the screen's edges.
- Migration `202610201813_app_meta_instance_id`: `app_meta.instance_id` (String(36), null), and
  one UUIDv7 for the existing row. Tested from the 0.12.0 fixture (the row keeps its values and
  gains an id); the 0.13.0 fixture `202610201813.sql` is built with a fixed id.
- New in the API: `GET /api/discover` (`DiscoverOut`, `meta/discover.py`). New in `web/hosts`:
  `is_local_name(name, own)`, `own_hostname()`, and `UNNOTED` (what never goes into "Recently
  reached at"). `scripts/image_common.sh` probes the route, and the name rule after setup.
- The agent: a new uv project, `kiosk/agent/` (package `sunroom_kiosk`): `config`, `schemas`,
  `app` (the guard and the routes), `state` (the `Agent`), `browser`, `screen` (moved from
  `kiosk/sunroom-screen`, removed in T8), `discovery`,
  `policy`, `events`, `updater` (the interface; T9 the real one), `platform/{base,fake}`,
  `testing` (`--fake` only), `cli`. Generated: `frontend/src/api/screen-openapi.json` and
  `screen-schema.d.ts` (`just api-types`). New recipes: `just kiosk-test`; `kiosk-lint` runs
  ruff and pyright strict on it; `just check` runs its tests; CI's `kiosk` job runs on
  `ubuntu-24.04`, `macos-15` and `windows-2025`.
- The wall page: `web/headers.csp(nonce, agent_port)`, `web/spa.screen_port`; in the frontend,
  `lib/screenAgent` (`noteScreenAgent`, called in `main.tsx`; `screenClient`,
  `createScreenClient`, `useScreenAgent`, `useScreenAgentEvents`, `screenReloadUrl`,
  `screenProgress`), `qk.screen.*`, and `lib/update`'s reload going to the launcher's address.
- The screen's own pages: `frontend/src/screen/` (`main.tsx`, `ScreenApp.tsx`, `route.ts`,
  `pages/`), `screen.html`, `vite.screen.config.ts`; `pnpm build` builds them after the app;
  `ui/ToastRegion` moved out of `ui/StatusLayer` (which re-exports it) so they load without the
  PWA; This Screen's Wi-Fi list is `WifiChooser`, shared. `just kiosk-dev` (the pretend agent with
  Vite's pages on 5174) and `just kiosk-build` (the pages, then the wheel). The e2e server starts
  the agent with `--fake pi` on 4174, finding the test server; `screen-shell.spec` walks the pages
  on both walls and a laptop, and `just screenshots` takes them (`screen-*`).
- The installer: `kiosk/files/` (the unit, the labwc block, the XDG entry, the udev rule,
  modules-load, the NetworkManager drop-in, sudoers, avahi, the compose file and `.env`, the root
  helper `sunroom-kiosk-root`); `install.sh` gains `--dry-run`, `--agent-wheel` and the Linux path;
  `uninstall.sh` uninstalls the agent with uv and removes the root helper, its sudoers rule and the
  policy files. Gone: `kiosk/sunroom-kiosk`, `kiosk/sunroom-screen`, `kiosk/systemd/` and
  `backend/tests/test_kiosk_screen.py` (its tests are the agent's `test_screen.py`).
  `sunroom-kiosk` with no command runs the agent; `sunroom-kiosk policy [--url]` prints the
  browser's policy. The agent's `tests/test_files.py` checks the files against the agent (the root
  helper's keys and paths, sudoers, the unit, the autostart block); CI's `kiosk` job runs the
  installer's dry run; `kiosk-lint` compiles the root helper.
- Releases: `release.py github` (`just github-release`, also in `just release`), the agent's
  pyproject and `uv.lock` in `release.py`'s release files, `.github/workflows/release-assets.yml`
  (`contents: write`, SHA-pinned actions; a pre-release tag makes a draft pre-release, for the
  owner's one test), the deploy skill's GitHub Release step and its report line, RELEASING.md.
  Dependabot now covers `kiosk/agent`.
