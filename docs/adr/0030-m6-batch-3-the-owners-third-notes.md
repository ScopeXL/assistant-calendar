# ADR 0030: The owner's third notes (M6, batch 3)

- **Status:** Accepted
- **Date:** 2026-10-13

## Context

- Sunroom 0.8.0 went on the owner's wall and phones, and a day later they sent a third set of
  notes, most of them about the header, the rail and the Add panel, with a request to audit the
  whole UI for clutter. `docs/M6-batch-3.md` turns them into tasks and records the decisions; this
  ADR keeps the ones that change an earlier decision or that a later session would otherwise have
  to rediscover (PLAN §15, M6 → 0.9.0).

## Decision

| Question | Decision |
|---|---|
| The live icon | A header draws it only while something is wrong: reconnecting, checking every 30 seconds, or offline. Connected draws nothing and keeps no room for itself, on the wall's header and the phone's Calendar header alike (this supersedes ADR 0028's "one icon in the corner, always"). About → Connection keeps the icon with its words in every state. The 2-second settle stays, so a room switch on the kiosk never flashes it. The page's root carries the stream's raw status (`html[data-stream]`, set in `lib/live`), which is how an end-to-end test knows a screen is hearing updates now that there's no icon to look for |
| The pointer | The page hides it, not the Pi: `lib/pointer` marks the root `data-pointer="hidden"` three seconds after the last mouse move and at once on a touch or a pen, on the kiosk's shell and on the screens before pairing (`/display`); a mouse move brings it back. A laptop in the display shell keeps its pointer. labwc's `HideCursor` rule (0.8.4) and `unclutter` stay for the moments before the page loads. The mark is on the root, not the shell, because the Add panel, the PIN pad and the keyboard are drawn beside the shell; the root remembers that it was hidden, because the kiosk remounts its shell on a room switch and the pointer would flash back each time; and a pointermove that goes nowhere is ignored, because Chromium sends one whenever the page changes under a resting pointer |
| Remembering the view | Per screen, in that browser's `localStorage`, not on the server: the board's view, which week, day or month, the people filter, the Week layout and zoom, the Today panel and the rail (`sunroom.display.view`, versioned and checked field by field), and the room the screen is in (`sunroom.display.room`). The display's store starts from it, so the remembered view is the first paint, before the server has answered. Every change is written, the idle reset too, and that is the design: the 2-minute and 5-minute rules are untouched, a screen that sat idle comes back home because that's what it was showing, and a screen refreshed mid-use comes back where it was. Never the open panel (drafts are a separate idea) and never Settings (its PIN grant may be gone) |
| When it starts | A household setting, `display_start`: **Where it left off** (`last`, the default) or **The home view** (`home`). With `home` a screen keeps nothing at all, rather than keeping it and ignoring it: the next start then has nothing to draw before the setting is known, so there's no flash of the old view. The first start after the setting changed while a screen was off is the one time that can happen. The setting is read once per page load (a module flag, since the kiosk remounts its shell between `/display` and the rooms); changed while a screen is in use it doesn't move the screen, it only starts or stops the keeping |
| The room at a restart | The Pi's launcher and its nightly restart always open `/display`, so a page that opens at home goes to the remembered room, once. A reload in place keeps its address and needs nothing. A remembered room whose feature was since turned off goes home by the rule every room address already follows |
| The city search | "Your city" (it was "Your town"), searching as you type: from 2 characters, 350 ms after the last key, with the last answer kept on screen until the next arrives so the list doesn't blink. The places are listed under the field in the page's flow, never a floating list: the wall's keyboard and a phone's sheet both need the page to make room for them. No Search button. A plain labelled field over a list of buttons, with a live status line, rather than an ARIA combobox: the rows are ordinary buttons to a screen reader and to the tests, and on a laptop the arrow keys still walk from the field into the list. The limit rises from 10 to 30 searches a minute per device, since one name is now a few searches. Open-Meteo matches 2 characters exactly and 3 or more loosely, so an empty answer reads "Keep typing…" under 3 and "Nothing by that name. Try the nearest city." from 3 |
| The test server's places | In test mode (`just dev`'s `.env`, `just seed`, the end-to-end runs) the weather never touches the network, and its city search knew two made-up places, so a real city "wasn't found" in development while Docker, which refuses test mode, found it. The fake now answers any name with one made-up place called that, in Sample State, a little apart for each name; the two sample places still answer "Sample", and a name starting with "Nowhere" finds nothing, so the empty answer can be seen |
| The wizard's pair step | Removed (this supersedes the step ADR 0006's first run ended on). The wall already shows **Pair This Screen** with its code the moment setup completes (it polls the setup status), and a phone's More → Pair a Display or the household password on the screen pair it at any time, so the step only made setup wait for a screen that might not be up yet. The steps are 1 of 6 to 6 of 6, and "You're Set" says where the code goes |
| A Pi that runs setup itself | Not a paired screen, and nothing in this batch changes that: `POST /api/setup` signs the browser that ran it in as a parent's phone, and a device's kind never changes. The kiosk can't start the wizard anyway (no address bar; before the household exists `/display` shows only "Set Up Sunroom on Your Phone"). If someone did, the way back is Settings → Phones & Screens → sign that phone out, then pair the screen properly |
| The rail's top | The mark alone, 48 px, centred like the rooms' icons, in a block exactly `--header-h` tall with the same bottom rule as the header, so the two rules meet. The word "Sunroom" leaves the rail (the mark keeps "Sunroom" as its name for a screen reader), and so does the fold button. This supersedes ADR 0029's "the brand (the mark over the name) and Hide the rail". `ui/Brand` keeps only the lockups that write the name |
| The rail's bottom | Settings is one `--tap` row (56 px) with a top rule: the gear (or padlock) with "Settings" beside it in the full rail, the gear alone folded. It lines up with the tips strip. Add is a 64 px circle with "Add" under it in the full rail and a 56 px circle folded, the size of a room's icon cell |
| The header's toggles | **Hide the rail** / **Show the rail** at the header's start, before today; **Hide the Today panel** / **Show the Today panel** at its end. One component draws both, the same bordered square, so they read as a pair; each sits at the edge nearest its panel and its icon faces that panel, and in a mirrored shell (the rail on the right) they swap ends. Both say `aria-expanded`. Neither is in portrait |
| The fold's motion | It was meant to ease in 0.8.0 and didn't: the rule that crossfades every surface (`:root[data-motion-ready] [data-surface]`, specificity 0,3,0) resets `transition` a moment after first paint, and the rail is a surface, so its own `width` transition (0,1,1) was lost. The rail's rule now out-ranks it and carries the crossfade too. With the width, each room's height eases, the words under the icons fade and give up their height, and the Add circle settles to its size. The words stay in the page when folded (no height, no ink) rather than becoming `sr-only`: they can fade, and a room keeps its name. Instant under Reduce motion, and never on first paint |
| The header's middle | No title for a room the rail already names (Calendar, Lists, Tasks, Meals, Countdowns, Photos, Settings) and no second line anywhere; this supersedes ADR 0029's "the room's title with one quiet line under it". The h1 stays, for screen readers only, so a room is still found by its heading. A page the rail can't name keeps a one-line title after its way back (`visibleTitle`): a list, Saved Meals, Stars & Rewards. Counts and spans that were subtitles moved into the page ("4 to get" over a list's items, "8 photos" over the grid) or went (the Meals week's span: its rows carry their dates). `RoomHeaderSpec` lost `subtitle` and `counts`; `notice` ("Drop on a day") is a pill beside the controls instead of replacing the title. **The owner may yet prefer every room to keep its name in the header**: it is one prop on each room to bring them back |
| The Calendar's header | After today and a rule: the arrows around This Week (Today, This Month) and, on the Week view, Agenda · Hours as two icons. At the right: Filter, then the view switch. No month, year or span: the day heads carry the dates, the Month view gets its month's name as a caption over its weekdays and the Day view its day's name over the timeline, the two views that would otherwise show bare numbers. The board's own toolbar is gone (this supersedes ADR 0029's "what stays with the board"); only the plugins' quiet pills remain above the days, and that row takes no room until a pill has something to say |
| Filter | One button for the people (and later calendars or kinds): a funnel, the word "Filter" from 112rem of header width, the chosen people's avatars and a darker border while a filter is on, named "Filter: Mia, Leo". Its menu: Everyone (a radio row), then each person as a checkbox row with a check; several at once; it stays open while choosing and closes on Everyone, Escape, the button, or a press elsewhere. Not `aria-pressed` as well as a menu button: the name says who. Hidden on People and Today, and in a household of one. Someone who has left the household is dropped from a remembered filter when it's read |
| The menu | `ui/Menu`, lifted from the View menu: `role="menu"`, radio and checkbox rows, a named group, the arrows, Home, End, Escape and Tab. A press outside closes it and its click is swallowed (`swallowFollowingClick`), so a tap on the board never also opens Add. Not a backdrop element as planned: the header is a size container, which contains fixed boxes, and a backdrop in the page's own layer would have covered the menu |
| The Hours zoom | On the grid, not in a toolbar: Zoom out · Fit the day · Zoom in at the grid's bottom corner, outside the scroller. A row, not the planned stack: stacked it was 204 px tall and covered the last column from 6:30 PM at the fitted zoom; as a row it covers 10 PM to midnight. The grid hands it its own limit, so the `hoursMaxZoom` store is gone |
| The header's type and spacing | The date 24 px bold on the time's baseline, the time 40 px, the temperature 32 px; 24 px between today's three things, a 2 px rule with 24 px either side, 16 px between the room's groups, 12 px before and inside the end zone, 24 px at the sides. The date doesn't grow: at 1920 px Standard with the panel open the one row has about 58 px to spare in the worst case measured (Wed, Sep 30, 12:30 PM, the Week view, four people filtered). As one row the header is exactly `--header-h` tall whatever a room puts in it (its vertical padding is 4 px there, since a bordered group is 12 px taller than a button), and `--header-h` is `max(5rem, var(--tap) + 1.5rem)`, so the rule under it meets the rail's at every text size |
| Settings navigation | 384 px (`w-96`, 24rem), each name on one line: "Calendars & Accounts" wrapped at 320 |
| Google's keys | In the **Sign in with Google** step of Add an account, the only flow that needs them (the secret address and the helper's key file don't; the server refuses the start without them). With none saved the step shows the two fields and **Save keys and continue**; with them saved, "Keys saved" with **Change keys** and **Remove keys**, then **Sign in with Google**. This supersedes ADR 0029's row on the Features page and its sheet. The sheet of an account that signed in this way can change the keys too, but not remove them: that would stop the account. The plugin still names the group in `ownSettingGroups`, so the generic Features form leaves the two fields out; `settings.features` stays in the registry with nothing using it. The export still masks the secret |
| The Add panel's shape | Three parts 32 px apart, their rows 16 px apart: what and who (the main field, Who), **When** (Day, Time, How long, Repeats) and **Details** (Calendar, Color, More…). The first has no visible heading: it starts with the form's main field, and "What and Who" over "What, when, who" said the same thing twice; it is still a named section for a screen reader. Every kind's form has the same three parts |
| Value rows | Time, How long, Repeats, Calendar and Remind are **value rows** (`ui/ValueRow`): the label at the left, what's chosen on one button at the right, the picker opening in place under the row. This narrows ADR 0029's "nothing behind a chip that has to be opened first" to "nothing behind a chip that *looks like a choice*": a value row says what's chosen on its face. Chips stay where a few fit one line: Who, the Day strip, Last day, Which list, Which meal, Stars |
| Lists, not chips, inside a picker | The choices of Repeats, How long, Calendar and Remind are a list, a row each with a check on the chosen one (`ChoiceList`, a radio group). The plan drew How long's as one line of chips; five lengths at the wall's sizes are 777 px in a 568 px box, so they would have wrapped, which is the thing this task removes |
| The likely times | Gone (this supersedes ADR 0029's "a chip for no time, the likely times, and Pick a time"). Time is the All day chip and one button; its picker's hours and minutes are two taps, in four columns, with Done. A task's Due and a routine's Starts are the same field |
| Labels and openers | A row's label is one quiet style everywhere (`ui/Field`: 20 px soft ink on the wall, 14 px on a phone, where the plan said 13), and `TextField`, `DayField` and the value rows use it, so a label stops looking like a chip. A chip that opens something in place (`opener`: Pick a date, More…, Another day) is outlined with a chevron that turns, and never filled like a choice |
| Color | A row of dots for an event and a countdown (`ui/ColorDots`): the person's own first, then the eight, tap-sized, named by their words for a screen reader, the chosen one ringed. Nine chips with words were three lines |
| A meal | One field, "What's cooking": what's typed is the name and the search of the saved meals, which sit under it as one scrolling row of chips. Tapping one fills the field and links it; so does typing its name in full; changing the words unlinks it. No "Saved Meals" heading and no second box. Who cooks starts on Anyone. Opened from a day's cell, the day and the meal are value rows. New List has the same shape: one field, the usual names as chips that fill it |
| The same pickers everywhere | An item's sheet picks its day with the Day strip (it had its own row of weekday chips), and a routine's Starts and Shows for are the time and length fields (it had seven fixed times) |
| The keyboard's top row | The wall keyboard's row for accents takes no room until a key is held (it kept 56 px empty for suggestions that were never built); `--osk-h` follows the keys' measured height through a `ResizeObserver`, so the panels' padding follows |

## Consequences

- `household` gains `display_start` (default `last`): one migration for the batch,
  `202610131907_household_display_start`, tested against the 0.8.0 fixture database.
- `just screenshots` clears a page's remembered view before every load (an init script in the
  spec): its shots are of screens as they first open, and a remembered zoom or fold would carry
  from one into the next.
- An end-to-end test that waits for a screen to hear live updates reads `html[data-stream="live"]`
  (`hearsLive` in `e2e/shell.spec.ts`), not the icon.
